# Memory infrastructure: products, frameworks, and managed services

Observation date: **2026-10-12**. This document uses public primary documentation, papers, and public repository source. It distinguishes current implementations from historical papers and from vendor claims. It is an architecture survey, not an independent benchmark or a claim that a local approximation reproduces a vendor's service.

## The comparison that matters

“Memory” covers several different mechanisms. A useful comparison separates **capture**, **write policy**, **durable representation**, **retrieval**, **context assembly**, and **lifecycle control**. A product can do one well without doing the others. In particular, an agent session store persists messages; a vector database retrieves records; a memory policy decides whether an observation should become a durable fact, update a profile, remain an episode, or be discarded. This decomposition is an analytical framework, illustrated by the different contracts below rather than a claim that every vendor uses these exact layers.

| Mechanism | Durable object | Representative systems | What it contributes |
|---|---|---|---|
| Session persistence | Ordered messages, tool calls, checkpoints | OpenAI Agents SDK sessions; LangGraph checkpointers; ADK sessions | Continuation and recovery |
| Fact extraction | Small attributed statements | Current Mem0; Memory Bank; AgentCore semantic strategy | Compresses interaction history into retrievable claims |
| Profile maintenance | User/entity fields or curated prompt context | Memobase; Supermemory profiles; LangMem profiles | Makes generally applicable context available without guessing a search query |
| Temporal graph | Entities, dated relationships, source episodes | Graphiti; Zep | Entity continuity, changing relationships, historical questions |
| Evidence-backed consolidation | Facts → observations → standing answers | Hindsight; current Zep observations | Moves synthesis off the request path while preserving supporting evidence |
| Agent-authored files | Markdown, source links, versions, skills | Current Letta; ReMe; memU | Editable, portable knowledge with ordinary file/Git tools |
| Experience/procedure memory | Situation, action sequence, outcome, reusable procedure | ReMe research; MemOS local layers; LangMem episodes/prompts | Transfers useful behavior rather than only personal facts |
| General search infrastructure | Vectors, text indexes, metadata, graph edges | Qdrant; pgvector; Pinecone; base Weaviate | Supplies retrieval/storage primitives; memory policy remains an additional layer |

The examples are substantiated in the product sections. Two recurring distinctions are essential: **append-only extraction does not prohibit an explicit delete API**, and **a self-hostable client or local binary does not prove that the memory engine is open source**.

## Mem0: current additive memory versus the historical CRUD algorithm

**Role and version boundary.** The 2025 Mem0 paper describes extracting salient information and reconciling it with existing memories; this is the historical source of the frequently repeated `ADD / UPDATE / DELETE / NOOP` architecture. Current repository documentation explicitly announces an April 2026 change to single-call, additive extraction, entity linking, hybrid search, and temporal retrieval. The repository also says the reported managed-platform scores include proprietary optimizations absent from the source SDK. Treat these as distinct systems when designing experiments. [2025 paper](https://arxiv.org/abs/2504.19413), [current README](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/README.md)

**Write path, source verified.** The Python SDK builds a session scope, fetches ten recent messages, embeds the incoming conversation, and retrieves ten similar existing memories. One LLM call sees the existing facts, recent messages, and new messages. It emits candidate memory texts; the code batch-embeds them, removes exact text-hash duplicates within the current batch and the retrieved existing set, attaches scope/timestamps/attribution, and inserts records. It records history and entity links only for successfully persisted records. This is local duplicate suppression around the retrieved neighborhood, not a demonstrated global semantic uniqueness constraint. [Extraction/persistence implementation](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/mem0/memory/main.py#L920)

**Retrieval, source verified.** The inspected SDK over-fetches semantic candidates with `max(limit * 4, 60)`, optionally queries a backend keyword index, normalizes keyword scores, and computes entity boosts. Crucially, its final candidate list is built from **semantic hits**; keyword/entity signals rescore that list. The scoring function applies the semantic threshold before combining signals, then normalizes the sum by the active signals' maximum. Therefore, this particular implementation is not equivalent to an RRF union of independent lexical and dense candidate lists: a lexical-only hit can remain absent. A later optional reranking stage and provider capabilities should be held fixed in comparisons. [Candidate construction](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/mem0/memory/main.py#L1642), [scoring](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/mem0/utils/scoring.py)

**Representation and scope.** Public code stores text, embeddings, metadata, creation/update timestamps, optional attribution and expiration, and history. User, agent, and run scopes constrain access at the SDK query level. These identifiers organize records; an application still needs to bind them to authenticated callers. Image/document ingestion is documented for the platform, including images and MDX/TXT/PDF inputs; do not infer that every SDK/backend combination shares the same multimodal support. [SDK methods and metadata](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/mem0/memory/main.py), [platform multimodal contract](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/docs/platform/features/multimodal-support.mdx)

**Graph and forgetting.** Current platform documentation describes an always-on native entity↔memory graph that boosts retrieval and no longer requires an external graph database or a separate `relations` response. This supersedes the older external Neo4j-style integration description. Platform memory decay is separately opt-in, a bounded relevance multiplier with access reinforcement; it does **not** delete records. The SDK still exposes explicit updates/deletes and filters expired records. Distinguish four operations: adding changed evidence, ranking current evidence, suppressing expired evidence, and actually deleting stored evidence. [Current graph documentation](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/docs/platform/features/graph-memory.mdx), [decay contract](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/docs/platform/features/memory-decay.mdx), [SDK lifecycle methods](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/mem0/memory/main.py#L1938)

**Architecture lesson.** Additive storage can reduce destructive write mistakes, but moves conflict handling toward retrieval, time interpretation, and answer synthesis. A reproducible comparison should have separate historical fact-upsert and current additive-hybrid variants; it should not attach the vendor's current benchmark numbers to either approximation.

## Graphiti and Zep: related, but not interchangeable

### Graphiti's inspectable temporal graph

Graphiti accepts episodes such as messages, text, and structured JSON, extracts entities and relationships, resolves them against existing nodes/edges, persists provenance, and supports optional communities. Its public ingestion separates node extraction/resolution from edge extraction/resolution; the latter can return resolved, invalidated, and new edges. The commit also includes **sagas**, linking a sequence of episodes and incrementally maintaining a bounded summary. [Graphiti source](https://github.com/getzep/graphiti/blob/0a3b1711b018e5590cf5c44a3ee3e67d6733ee13/graphiti_core/graphiti.py), [episode/node types](https://github.com/getzep/graphiti/blob/0a3b1711b018e5590cf5c44a3ee3e67d6733ee13/graphiti_core/nodes.py)

A fact is more than a vector: its edge carries a fact string, embedding, source/target entity identifiers, associated episode identifiers, partition `group_id`, and temporal fields including `created_at`, `expired_at`, `valid_at`, `invalid_at`, and the producing episode's reference time. The important architectural idea is the separation of **when a claim applies** from **when the system acquired or retired its representation**. This supports corrections, backfills, and historical questions without interpreting ingestion order as real-world order. [Edge schema and persistence](https://github.com/getzep/graphiti/blob/0a3b1711b018e5590cf5c44a3ee3e67d6733ee13/graphiti_core/edges.py#L259)

Retrieval is configurable rather than one fixed “graph search”: public recipes combine BM25, cosine similarity, and optionally breadth-first traversal, with RRF, maximal marginal relevance, node-distance, or cross-encoder reranking depending on the recipe. Separate configurations query edges, entities, episodes, and communities. The availability of a graph does not imply every request performs a multi-hop traversal. [Search recipes](https://github.com/getzep/graphiti/blob/0a3b1711b018e5590cf5c44a3ee3e67d6733ee13/graphiti_core/search/search_config_recipes.py)

The library is Apache-2.0 and self-hostable; its database and model adapters remain deployment choices. `group_id` partitions the graph, while application identity, authorization, provider credentials, and retention policy remain deployment responsibilities. Public deletion methods exist, but expiration of a temporal edge is not the same operation as erasing its underlying source episode. [README/deployment options](https://github.com/getzep/graphiti/blob/0a3b1711b018e5590cf5c44a3ee3e67d6733ee13/README.md), [group deletion](https://github.com/getzep/graphiti/blob/0a3b1711b018e5590cf5c44a3ee3e67d6733ee13/graphiti_core/nodes.py#L178)

### Zep's managed context layer

Current Zep v3 presents a broader service: user and shared Context Graphs, a Context Lake served through its Konig database service, business-data ingestion, threads, summaries, observations, governance, and prompt-ready Context Blocks. Graphiti is a public framework behind this lineage, not a source disclosure of all managed Zep internals. [Current documentation map](https://help.getzep.com/v3/llms.txt)

Zep documents a write pipeline that extracts entities and facts from episodes, resolves them against existing graph state, updates summaries, and persists the result. Beyond individual facts, its observations identify patterns across evidence, such as repeated preferences, commitments, and state changes. Retrieval can return a Context Block rather than asking the caller to manually combine every search result. These are relevant handoff primitives: they construct compact task context, but do not establish that a downstream agent has completed the task. [Graph creation](https://help.getzep.com/v3/how-graph-creation-works), [observations](https://help.getzep.com/v3/observations), [context retrieval](https://help.getzep.com/v3/retrieving-context)

Zep's provenance model is unusually explicit. Facts link to source episodes, including later episodes reaffirming or invalidating them; observations link to their supporting episodes; summaries link to their source messages. Deleting an episode removes an associated entity or edge only when no supporting episode remains. Metadata is projected onto derived artifacts for filtering and access controls, with important distinctions between a union of effective metadata and per-episode filter matching. This means raw-event provenance participates in governance rather than being merely a citation decoration. [Episode metadata projection](https://help.getzep.com/v3/episode-metadata-projection), [source traceability](https://help.getzep.com/v3/source-traceability)

**Architecture lesson.** Entity-centric memory benefits when a question spans people, systems, projects, and time. It also creates two extra correctness obligations: mistaken entity merges can contaminate many answers, and deletion/access changes must propagate through artifacts derived from multiple sources. A graph should be evaluated on those operations, not only on successful multi-hop answers.

## Letta / MemGPT: from virtual context tiers to Git-backed agent memory

**Historical system.** MemGPT introduced virtual context management: an agent uses tools to move information between limited in-context memory and larger external stores, with control-flow mechanisms for continuing work. Letta V1 made memory blocks editable and attachable, kept all messages durable, and exposed archival retrieval. This historical core/recall/archive model remains useful as a representative experiment. [MemGPT paper](https://arxiv.org/abs/2310.08560), [V1 stateful-agent documentation](https://docs.letta.com/v1-sdk/concepts/stateful-agents)

**Current version boundary.** The present `letta-ai/letta` README says that the V1 server is retired on an archive branch and active source is in `letta-ai/letta-code`. A survey that describes only the old Python server as current Letta misses a material architecture change. [Repository migration notice](https://github.com/letta-ai/letta/blob/5bcdd177d70fa2b31a754cfcd801e77b2e1ab16a/README.md)

**Current representation and retrieval.** Agent memory lives in a Git repository projected onto a working computer by MemFS. Creation-time memory entries become Markdown files under `system/`; those files are inserted into the system prompt each turn. Other files are represented by a file tree and read on demand. Memory is agent-owned and portable across conversations, models, and computers. The SDK documents commit-and-push as the durability boundary for edits. This is a policy of a small always-present working set plus agent-directed navigation of a larger file hierarchy, not simply vector recall of archival passages. [Current memory contract](https://docs.letta.com/agent-sdk/memory), [public runtime](https://github.com/letta-ai/letta-code/blob/7203ec6a2b2dcf1b9fed13179539a5cf5a703edf/src/agent/memory-runtime.ts)

**Write and consolidation policy.** The agent edits its own memory. “Dreaming” delegates review of recent conversation and consolidation of lessons to background subagents. Triggers can be disabled, tied to a step count, or tied to compaction; behavior can remind the foreground agent or launch automatically. This moves consolidation out of the interactive turn while retaining an inspectable artifact. A local implementation should record which conversation prefix each dream saw, so late-running dreams cannot silently incorporate future evaluation evidence. [Dreaming configuration](https://docs.letta.com/agent-sdk/memory), [current harness README](https://github.com/letta-ai/letta-code/blob/7203ec6a2b2dcf1b9fed13179539a5cf5a703edf/README.md)

**Sharing and conflict controls.** Hosted shared repositories can be attached temporarily to a session or persistently to an agent. File mutations create commits; reads can target a ref; updates support a content-hash precondition to reject stale writes. The hosted shared-repository API is a cloud feature; the docs describe custom Git remotes for self-hosted sharing. Detaching a repository removes the attachment, while deleting a repository is a separate operation. Git version history is valuable for inspection, but a file deletion in a new commit is not by itself evidence that sensitive data vanished from all previous revisions. [Shared repository SDK](https://docs.letta.com/agent-sdk/repositories)

**Deployment and fidelity.** The current harness is Apache-2.0 and offers cloud/local backends; cloud stores agent identity, memory, and conversations while execution may occur on different computers. It provides message search and skills as adjacent context sources. These inspected contracts support “agent-authored, versioned memory plus background consolidation”; exact production retrieval ranking and all cloud retention details are not established here. [Deployment/source README](https://github.com/letta-ai/letta-code/blob/7203ec6a2b2dcf1b9fed13179539a5cf5a703edf/README.md)

## Hindsight: retained evidence, consolidated observations, and precomputed answers

**Role and input.** Hindsight exposes `retain`, `recall`, and `reflect`, separated by how much interpretation they perform. Retain processes conversations/documents into contextual facts and entities. Facts distinguish the bank agent's own experiences from facts about the outside world; first-person grammar alone does not determine ownership. The current retain contract accepts ordered text/image/file content blocks and explicitly encourages preserving contextual attribution. [Retain documentation](https://hindsight.vectorize.io/developer/retain)

**Representation.** A bank contains source documents/chunks, facts, entity associations, and semantic, temporal, entity, and causal links. Event time is distinguished from learning time. The primary backend is PostgreSQL, using pgvector/HNSW, full-text indexes, relational records, JSONB, and graph traversal through SQL; the current docs also describe an Oracle deployment alternative. It is inaccurate to assume that a separate graph database is required. [Retain source documentation](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/retain.md), [storage](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/storage.md)

**Recall is an explicit retrieval pipeline.** It runs semantic, keyword, graph, and temporal retrieval, fuses ranked candidates, applies a cross-encoder when configured, adjusts relevance with bounded recency/temporal/proof signals, and packs memory into a token budget. The native PostgreSQL keyword backend is documented as `ts_rank_cd`, not true BM25; other backends offer BM25. A temporal query first narrows to a date window, then selects relevant candidates with spread across time buckets. The public docs expose enough detail to implement a meaningful representative baseline without pretending it is the hosted service. [Pinned retrieval design](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/retrieval.md)

**The ranking details matter.** The documented post-rerank formula is a relevance score multiplied by bounded recency, temporal, and proof-count factors, instead of an unrestricted recency bonus. Search depth (`budget`) is separate from output size (`max_tokens`). The token packing described by this commit skips oversized lower-priority items, but returns the top item whole if nothing fits; only fact text counts toward this budget. Therefore, `max_tokens` is not a hard upper bound on the fully serialized response, metadata included. [Ranking and token-packing contract](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/retrieval.md)

**Consolidation.** After retention, a background process creates or refines observations backed by source memories, quotes, and proof counts. Contradictions can be represented as a change in understanding instead of deleting the earlier fact. Near-duplicate reconciliation compares observations within the same tag scope; the documented default similarity threshold is 0.97, with a focused merge/keep check. Observations can become stale when new unconsolidated evidence arrives, and reflect is instructed to verify stale observations against raw facts. Scope choices are consequently part of the learning algorithm: per-session tags can prevent cross-session consolidation unless explicitly configured otherwise. [Observation lifecycle](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/observations.mdx)

**Mental models and reflect.** A mental model is a stored answer to a deliberately chosen question, refreshed as knowledge changes; fetching it is a database read rather than fresh reasoning. Reflect performs an evidence-gathering agent loop over mental models, observations, facts, and source expansion, then returns a response with evidence identifiers and optional structured output/trace. It can be steered by a bank mission, disposition, and scoped directives. Those are model instructions and documented guardrails, not a proof that all generated judgments are true. [Mental models](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/mental-models.mdx), [reflect](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/reflect.mdx)

**Deletion and deployment.** Banks isolate memory; tags narrow visibility and observation scopes. Public docs include explicit memory/document lifecycle APIs and allow consolidation to be automatic or manually triggered after writes/updates/deletes. These provide the basis for lifecycle testing, but complete physical erasure across backups and all derived outputs is a deployment question. The engine is MIT licensed and self-hostable; hosted service and external model calls are separate trust boundaries. [Repository](https://github.com/vectorize-io/hindsight/tree/f843f173bb41f001e322cc83c917371639e47fbf), [consolidation controls](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/observations.mdx)

**Architecture lesson.** Hindsight makes a valuable separation: source evidence, accumulated beliefs, and task-shaped standing answers have different freshness and cost properties. A system can pay more on ingestion and background consolidation to return compact context cheaply, provided the dependencies remain inspectable and stale material is detectable.

## Supermemory: facts, profiles, documents, and filesystem views

Supermemory explicitly distinguishes submitted **documents** from extracted **memories**. Its documented graph connects facts with `updates`, `extends`, and `derives`: replacement of current truth, compatible enrichment, and inferred knowledge. Current retrieval uses fields such as `isLatest` to prefer current facts while retaining history. This is a graph of facts and their evolution; it should not be silently modeled as only entity–relation–entity triples. [Graph memory contract](https://supermemory.ai/docs/concepts/graph-memory)

Ingestion supports conversations, files, URLs, and connected sources. Current public material describes PDF/image extraction, audio/video processing, and code-aware handling. The pipeline distinguishes a memory-building path from document-only retrieval (“SuperRAG”). Dynamic dreaming groups coherent related content for continued extraction/linking/inference; an instant mode processes the document immediately for cases requiring the next read to see it. A successful upload and finished document indexing therefore should not automatically be interpreted as every derived memory being current. [Processing pipeline](https://supermemory.ai/docs/concepts/how-it-works), [API contract](https://api.supermemory.ai/reference), [public repository description](https://github.com/supermemoryai/supermemory/blob/8c70ffdc8ba026ab3f11b403aaf943392e915ec8/README.md)

Profiles provide standing user/tenant/task context, separating relatively stable information from recent activity. Search can target memories, document chunks, or both; related graph context and reranking are available. The product also exposes SMFS, a filesystem-shaped view agents can search with ordinary tools. Those are different **context assembly interfaces** over memory; they are not evidence of three unrelated storage systems. Namespaces are the current isolation vocabulary; older examples use container tags. [Profiles](https://supermemory.ai/docs/concepts/user-profiles), [search](https://supermemory.ai/docs/recall/search), [SMFS](https://supermemory.ai/docs/smfs/overview), [namespace migration map](https://supermemory.ai/docs/llms.txt)

Automatic temporal expiry, supersession, and noise suppression are documented separately from explicit forgetting. The API also documents review of low-confidence derived memories. For a privacy-sensitive application, test deletion of a supporting document, the derived fact, the profile contribution, and any filesystem view independently; an advertised “forget” feature does not explain every cache or historical retention edge. [Memory operations](https://supermemory.ai/docs/recall/memory-operations), [inference review](https://supermemory.ai/docs/recall/memory-review)

**Openness boundary.** The public repository is MIT licensed, but the current local-server documentation states that server source is not in the public repository. Local is a distributed binary under a separate lite license, while enterprise uses proprietary models and managed infrastructure. Text memory can be processed offline with suitable local models after model download; URL ingestion uses a hosted reader. Do not call the complete Supermemory engine open source merely because its SDKs, plugins, or main public repository have permissive licenses. [Local versus enterprise](https://supermemory.ai/docs/self-hosting/local-vs-enterprise), [repository license](https://github.com/supermemoryai/supermemory/blob/8c70ffdc8ba026ab3f11b403aaf943392e915ec8/LICENSE)

**Fidelity.** The public sources substantiate API behavior and the conceptual lifecycle. The exact extraction prompts, graph storage internals, ranking weights, and proprietary model training are not fully established by the inspected public engine source. Benchmark results remain vendor-reported and should be evaluated against the exact model, context budget, dataset, and latency/cost accounting used.

## Cognee: connected memory as a configurable processing system

Current Cognee exposes `remember`, `recall`, `improve`, and `forget`; older and still-visible lower-level APIs include `add`, `cognify`, and `memify`. Its current architecture distinguishes content ingestion, code-symbol/dependency graphs, and session knowledge that can be distilled into accepted durable lessons. Plain text ingestion/retrieval/session storage can run without an LLM in the current quickstart; generated answers and media extraction may require one. This is a more specific claim than “all Cognee graph construction always calls an LLM.” [Current operations and architecture](https://github.com/topoteretes/cognee/blob/0ec7a9fa61c9ff04bf7e02e0d57af363a993a5e1/README.md)

Its public source exposes graph extraction, entity/description consolidation, feedback-driven improvement, and many retrieval strategies: chunks, summaries, graph completion, lexical/BM25, hybrid, temporal, code, skills, and agentic retrieval. These are selectable components, not one canonical policy that can be represented by a generic “Cognee = graph RAG” label. Application datasets/users/sessions determine which knowledge is written and queried. [Cognify implementation](https://github.com/topoteretes/cognee/blob/0ec7a9fa61c9ff04bf7e02e0d57af363a993a5e1/cognee/api/v1/cognify/cognify.py), [memify pipeline](https://github.com/topoteretes/cognee/blob/0ec7a9fa61c9ff04bf7e02e0d57af363a993a5e1/cognee/modules/memify/memify.py), [retrieval modules](https://github.com/topoteretes/cognee/tree/0ec7a9fa61c9ff04bf7e02e0d57af363a993a5e1/cognee/modules/retrieval)

The public core is Apache-2.0 and offers local/self-hosted deployment. However, the current README labels the bundled small-model extractor a demo, and the all-in-one PostgreSQL graph-store path a demo with a separately licensed production version. Choose the actual backend and license before claiming equivalent local/cloud capability. Deletion is exposed as `forget`; generic semantic conflict resolution and complete source-to-derived cascade guarantees require checking the chosen pipeline, not inferring them from the existence of a graph. [Deployment/license qualifications](https://github.com/topoteretes/cognee/blob/0ec7a9fa61c9ff04bf7e02e0d57af363a993a5e1/README.md), [forget implementation](https://github.com/topoteretes/cognee/blob/0ec7a9fa61c9ff04bf7e02e0d57af363a993a5e1/cognee/api/v1/forget/forget.py)

## MemOS: a family of memory components, not one database recipe

MemOS's Python abstraction explicitly supports textual, activation, parametric, and preference memories through a configurable MemCube. The cube can load/dump selected memory types, and uninitialized types remain absent. Therefore, the architecture's support for activation/parametric memory must not be paraphrased as “every conversation updates model weights or KV caches.” Which mechanisms run depends on the selected backend and configuration. [MemCube implementation](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/src/memos/mem_cube/general.py)

Current product-facing documentation emphasizes inspectable graph memory, text/images/tool traces/personas, composable knowledge-base cubes, asynchronous scheduling, and feedback-based corrections. It also distinguishes the Python/open-source core, hosted plugins, and local plugins. The local plugin lineage uses SQLite, FTS5 plus vector retrieval, task/experience memory, and L1 traces → L2 policies → L3 world models → reusable skills. These layers target agent behavior and task transfer as well as user facts. [Current README](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/README.md), [local layer design](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/apps/memos-local-plugin/docs/GRANULARITY-AND-MEMORY-LAYERS.md)

The public local-layer design distinguishes a **step**, a **subtask/episode**, and a **conversation turn**: successful action sequences should be grouped by continuity of the goal, not merely by a chat turn identifier. Retrieval can seek a similar state/action, a similar goal and successful episode, or an environment constraint. This is directly relevant when the desired output is a handoff: a preference profile alone cannot recover the commands, blockers, environment assumptions, and unfinished subtask needed for continuation. These are design claims in the repository, not independently validated effectiveness results. [Granularity and retrieval design](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/apps/memos-local-plugin/docs/GRANULARITY-AND-MEMORY-LAYERS.md)

A separate Dream module documents selecting unresolved motives such as unfinished goals or conflicts, retrieving memories around them, and persisting both a diary/trace and synthesized dream memory. It should be evaluated separately from generic periodic summary generation. The inspected sources expose editing/deleting/correction APIs, but no universal cross-backend conflict, retention, or physical-erasure guarantee is established here. [Dream module](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/docs/en/open_source/modules/dream.md), [license](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/LICENSE)

## Memobase: profile slots plus a chronological event record

Memobase centers the user profile rather than assuming every question starts with vector similarity. A profile has configurable topics/subtopics; ingestion buffers conversation blobs, then flushes them into profile updates and events. Events include profile deltas, creation time, and optional summaries/tags. This produces both a compact current profile and an account of how it changed. [Profile schema](https://github.com/memodb-io/memobase/blob/358c16bbc6d687937d79bc2f984a11c3be8da901/docs/site/features/profile/profile.mdx), [event schema](https://github.com/memodb-io/memobase/blob/358c16bbc6d687937d79bc2f984a11c3be8da901/docs/site/features/event/event.mdx)

Writes use extraction/merge prompts and can run asynchronously; the public server uses FastAPI, PostgreSQL, and Redis. The README says processed raw blobs are deleted by default unless configured for retention. This is a consequential fidelity trade-off: the profile/event layer is useful context but cannot always serve as a verbatim source archive. [README and flush semantics](https://github.com/memodb-io/memobase/blob/358c16bbc6d687937d79bc2f984a11c3be8da901/readme.md), [merge prompts](https://github.com/memodb-io/memobase/blob/358c16bbc6d687937d79bc2f984a11c3be8da901/src/server/api/memobase_server/prompts/merge_profile.py)

Whole-profile retrieval provides generally relevant personalization. Optional query-aware profile search asks an LLM which profile features matter—for example, location and allergies for a meal-related request—rather than requiring lexical overlap with the final answer. The docs explicitly acknowledge additional latency/cost. Profiles, events, blobs, and users have management APIs; scope is organized around project/user. It is Apache-2.0 and supports self-hosted and managed use. Current support for an arbitrary raw multimodal capture stream is not established by the inspected chat/profile path. [Profile search](https://github.com/memodb-io/memobase/blob/358c16bbc6d687937d79bc2f984a11c3be8da901/docs/site/features/profile/profile_search.mdx), [public API documentation tree](https://github.com/memodb-io/memobase/tree/358c16bbc6d687937d79bc2f984a11c3be8da901/docs/site/api-reference)

## ReMe and memU: current file-native memory designs

### ReMe

Current ReMe stores ordinary Markdown with frontmatter and wikilinks. Its Auto Memory flow derives a topic-named daily card for a session/date, links it from a day index, and preserves a source conversation record. Cards can contain preferences, facts, decisions and rejected alternatives, blockers, next steps, and reusable procedures. The source record intentionally omits tool-result and base64 blocks; it is therefore a filtered provenance record, not a complete execution audit. Image handling is configurable and disabled by default in the documented Auto Memory path. [Auto Memory](https://github.com/agentscope-ai/ReMe/blob/749c653f23bbe6791574dd8428fec6c49984574d/docs/en/auto_memory.md)

Auto Dream scans changed daily files within a configurable recent window and integrates a small number of high-value units into `digest/`. The integration vocabulary includes reinforcement, refinement, and correction. Failed source paths are not checkpointed as processed, allowing a later run to retry. This gives a concrete example of consolidation as an incremental background job with progress tracking, rather than repeatedly rewriting one global summary. [Auto Dream](https://github.com/agentscope-ai/ReMe/blob/749c653f23bbe6791574dd8428fec6c49984574d/docs/en/auto_dream.md)

A watcher converts Markdown into file nodes, line-addressable chunks, and a wikilink graph. Default search uses BM25 and link expansion; embeddings are optional. When enabled, keyword/vector recall is fused with RRF before neighborhood expansion. Files are the durable editable layer and indexes can be rebuilt, but the documented `reindex` operation rebuilds from accepted in-memory chunks rather than rescanning arbitrary filesystem contents. Deletions remove index/graph entries; some backends use tombstones compacted later. [Search/index lifecycle](https://github.com/agentscope-ai/ReMe/blob/749c653f23bbe6791574dd8428fec6c49984574d/docs/en/memory_search.md)

ReMe is Apache-2.0 and can run locally as CLI, HTTP, MCP, or embedded Python. It also has procedural-memory research and older lineages, which should not be conflated with the current Markdown system. Workspaces/profiles and host integration determine sharing. A file link is inspectable provenance, but does not automatically supply fine-grained access control over every linked source. [Current repository](https://github.com/agentscope-ai/ReMe/blob/749c653f23bbe6791574dd8428fec6c49984574d/README.md)

### memU

The current memU source describes personal memory stored as a wiki and skills extracted from host-agent histories. A scheduled adapter slices new session logs into self-contained jobs; the **host agent** decides what is worth retaining and writes memory/skill Markdown; a commit step submits those artifacts to a shared backend. The README explicitly says `MemoryService` makes no LLM/chat calls: its job is storage, embedding, and retrieval. This clean division is materially different from a managed memory API whose own extraction model owns the write policy. [Current source description](https://github.com/NevaMind-AI/memU/blob/166be9041aa4ba545bda84172e841241c7ca09ab/README.md)

Host instructions invoke progressive retrieval for future tasks, and hosts can share a local or cloud backend. The public README lists in-memory, SQLite, and PostgreSQL options and states that uninstalling integration/tooling preserves stored memories unless erasure is explicitly requested. The license text is Apache-2.0. Exact conflict handling, temporal ranking, and a general deletion cascade across learned skills are not established by this survey; those should be verified in the chosen version before operational use. [Developer integration](https://github.com/NevaMind-AI/memU/blob/166be9041aa4ba545bda84172e841241c7ca09ab/docs/developer.md), [README and license](https://github.com/NevaMind-AI/memU/blob/166be9041aa4ba545bda84172e841241c7ca09ab/LICENSE.txt)

## Managed cloud memory services

### Google Agent Engine / Agent Platform Memory Bank

Google's current documentation calls the service **Agent Platform Memory Bank** under Gemini Enterprise Agent Platform; older Agent Engine URLs may redirect. The core operation is extracting self-contained textual memories from conversations or multimodal inputs, consolidating them with existing memories in an identity scope, and retrieving all or similar facts. It also supports direct creation and consolidation of pre-extracted memories. This is an actual write policy service, unlike an in-memory ADK search example. [Current overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank)

Generation may be asynchronous or driven by continuous event ingestion with batching rules. Extraction can be guided by topics/examples. Scope is an explicit identity map, and the managed service documents memory revisions, TTL, and IAM conditions for restricting scopes. Source sessions preserve messages/tool actions separately; memory generation is a selected transformation over those events. Model region, storage region, access configuration, and application authorization need to be treated as separate deployment concerns. [Generation](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank/generate-memories), [overview and lifecycle controls](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank), [platform security boundaries](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale)

**Known/unknown.** The external extraction/consolidation/revision contracts are documented. Exact internal prompts, index configuration, ranking weights, and physical storage implementation were not established from public engine source. A local fact-manager analogue can test a policy family, but cannot claim managed Memory Bank fidelity.

### AWS Bedrock AgentCore Memory

AgentCore separates short-term **events** from long-term **records** derived by configured memory strategies. Actor and session identifiers organize event history; hierarchical namespaces organize long-term records. Strategies specify what kind of information is retained, and service documentation includes built-in strategies, customization, episodic processing, and operational record APIs. [Terminology](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-terminology.html), [organization](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-organization.html), [strategies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-strategies.html)

A particularly useful primary source is AWS's published **semantic-strategy prompt and schemas**. It distinguishes extraction from consolidation, and its inputs can include conversation roles and structured JSON events such as activity logs, profile snapshots, and system events. This demonstrates that memory extraction need not be restricted to chat transcripts. A captured activity should retain its source type and subject; blindly converting every event into a user assertion changes the semantics. [Published semantic extraction/consolidation prompt](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-system-prompt.html)

Long-term operations include ingesting content, retrieving/listing records, structured metadata, deleting records, and retrying failed ingestions. This is a managed service contract: storage internals are not established as open source by the existence of public SDK/examples. Explicitly test whether deleting raw events and deleting derived long-term memories are independent operations for the chosen resource/strategy configuration. [Long-term memory operations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/long-term-memory-long-term.html)

### Microsoft Foundry memory

Foundry documents a **preview** managed memory store with user-profile memories, chat summaries, and procedural memories. A store specifies chat/embedding deployments and extraction/retention options. It can be attached through a memory search tool or operated through lower-level APIs; item-level CRUD, default TTL, and direct remember/forget commands are documented. This goes beyond Semantic Kernel's vector-store abstraction. [Concepts and preview status](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/what-is-memory), [usage/API lifecycle](https://learn.microsoft.com/en-us/azure/ai-foundry/agents/how-to/memory-usage)

The current page also lists limitations, including no VNet integration for memory stores and API-version-sensitive creation options. Treat those as observed preview constraints rather than promises about future releases. A hosted-agent example retrieves before a model call and updates after the turn. [Scope/limitations](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/what-is-memory), [hosted-agent integration](https://learn.microsoft.com/en-us/azure/foundry/agents/quickstarts/quickstart-memory-hosted-agent)

Engram should be distinguished from a bare Weaviate vector database. The documented memory record has content, topic, processing group, project/user scope, custom properties, timestamps, and a retrieval score. It is automatically embedded and supports search plus explicit retrieval/deletion by identifier. This substantiates a memory-oriented API and processing configuration; it does not establish that every possible conflict or temporal inference is resolved correctly. **Capture design inference.** A desktop observation, a transcript, a human-authored note, an assistant statement, and a successful tool result are different kinds of evidence. A memory layer should preserve that distinction all the way to a task-context packet. None of the surveyed SDK contracts establishes that generic “multimodal input” automatically includes operating-system capture, permission handling, transcription, screen-text extraction, or authoritative action outcomes.

## Search and databases: distinguish capability from policy

Qdrant documents staged/hybrid queries and rank fusion; pgvector supplies exact/approximate vector search inside PostgreSQL; Pinecone namespaces partition stored data. These can implement excellent memory retrieval. Their storage/search primitives alone do not decide whether a newly observed address supersedes an older address, whether a preference should enter a standing profile, or whether a procedure learned from one success should be generalized. Those decisions belong to application logic or a separate memory layer. [Qdrant hybrid queries](https://qdrant.tech/documentation/search/hybrid-queries/), [pgvector](https://github.com/pgvector/pgvector), [Pinecone namespaces and multitenancy](https://docs.pinecone.io/guides/index-data/implement-multitenancy)

The same distinction applies to a graph database: storing timestamped edges does not automatically implement entity resolution, temporal contradiction handling, evidence propagation, or context selection. Conversely, Hindsight's PostgreSQL design demonstrates that a memory graph can be implemented without a separate graph database. [Hindsight storage architecture](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/storage.md)

Do not group all these infrastructure projects under one license label. A managed API, a permissive SDK, a copyleft database, a source-available server, and a proprietary downloadable binary are different artifacts. The exact engine/version/license should be recorded when selecting an implementation; the ledger above only labels components whose license text was inspected.

### 5. Hybrid retrieval should declare candidate and ranking semantics

Two useful, deliberately different baselines are:

```text
semantic-gated:
    C = dense_top_k(query)
    C = filter(C, dense_score >= threshold)
    score(c) = normalize(dense(c) + keyword(c) + entity_boost(c))

union-and-fuse:
    lists = [dense(query), lexical(query), temporal(query), graph(query)]
    C = union(lists)
    rrf(c) = sum(weight_i / (k + rank_i(c)) for lists containing c)
    C = rerank(query, top_candidates(C, rrf))
    score(c) = relevance(c) * bounded_freshness(c) * bounded_evidence(c)
```

The first captures a consequential property of the inspected Mem0 SDK; the second captures a family exemplified by Graphiti search recipes and Hindsight retrieval. A lexical-only implementation is a useful offline ablation, but cannot reproduce embedding behavior, neural reranking, or model-directed extraction. Derivation: [Mem0 scoring](https://github.com/mem0ai/mem0/blob/d26ba5e4518cef7fff3c66d4f715b21adf9feabe/mem0/utils/scoring.py), [Graphiti recipes](https://github.com/getzep/graphiti/blob/0a3b1711b018e5590cf5c44a3ee3e67d6733ee13/graphiti_core/search/search_config_recipes.py), [Hindsight pipeline](https://github.com/vectorize-io/hindsight/blob/f843f173bb41f001e322cc83c917371639e47fbf/hindsight-docs/docs/developer/retrieval.md).

## Requirements for activity-to-handoff experiments

These are proposed evaluation requirements, derived from the architecture differences above rather than vendor promises:

1. **Use two clocks.** Record event time and availability/ingestion time. A replay query must not see later messages, later corrections, later summaries, or background work computed from a future prefix.
2. **Preserve provenance and attribution.** Keep the source ID, speaker/actor, modality, source version, and extraction version. An assistant saying an action succeeded is not the same evidence as an observed successful tool result.
3. **Make memory policy visible.** Log each extraction, merge, invalidation, deletion, consolidation, and retrieval decision. Retain intermediate artifacts so “wrong answer” can be attributed to capture, extraction, retrieval, synthesis, or use.
4. **Keep sources and projections separable.** Raw activity, factual claims, user profiles, episodic summaries, learned procedures, and generated handoffs should be separate artifact types with dependency links.
5. **Scope before retrieval and consolidation.** Authorized source scope must constrain candidate generation and derived summaries, not merely filter the final prose after a cross-user synthesis has already happened.
6. **Evaluate forgetting transitively.** Ask whether a deleted statement survives in an observation, profile, skill, handoff, cache, vector index, or version history. Distinguish logical invisibility, physical deletion, and backup retention.
7. **Budget the complete context.** Measure serialized memory text, metadata, source links, prompt wrappers, and tool results. A provider's nominal fact-text token limit may exclude substantial overhead.
8. **Treat a handoff as a supported context packet.** Useful fields include objective, observed progress, decisions and constraints, rejected approaches, blockers, next steps, relevant artifacts, and source citations. Label uncertain or inferred fields. Producing this packet is not proof of successful task execution.
9. **Compare policies and components separately.** A common extractor can isolate retrieval/consolidation effects, but erases genuine differences in vendor write policy. Report both shared-extraction ablations and end-to-end variants when feasible.
10. **Do not turn vendor leaderboards into cross-product rankings.** Model choice, answer generator, judge, input truncation, top-k, time handling, source retention, and cost accounting can dominate the headline score. The source pins and configuration belong beside the result.

The strongest common design pattern is **retain verifiable evidence, derive multiple purpose-specific views, and make the selection/lifecycle policy explicit**. The main unresolved empirical question is not whether one storage shape is universally superior, but which combination produces the most useful, current, scoped, and inspectable task context under a fixed total cost.
